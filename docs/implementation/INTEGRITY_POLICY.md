## 1. The v6 Evidence-Enforced Build Law

The Hit DNA Music Intelligence Platform operates under strict epistemic truth laws. All published intelligence, analytics, percentages, and generated song blueprints must originate from auditable empirical facts or explicit user directives.

### Invariant Rules
1. **Zero Fabrication:** Never create, seed, mock, simulate, estimate, extrapolate, or fabricate production music research data, chart observations, song records, artist research, DNA values, archetype shares, percentages, evidence, citations, URLs, API responses, generation history, slang trends, chord/groove/arrangement patterns, or provider integration states.
2. **Deterministic Percentages (Denominator Before Percentage):** Every numerical statement presented as historical, current, statistical, comparative, trending, or evidence-based must be reproducible from persisted source records using versioned deterministic code. Every percentage requires numerator, denominator, qualifying cohort, coverage, and immutable source lineage.
3. **Strict Fixture Isolation:** Test fixtures are strictly confined to isolated test suites (labeled `TEST_FIXTURE`) and must never be referenced by production code, production loaders, or production UI components.
4. **No Silent Fallbacks or Hallucinations:** If data or credentials are unavailable, return typed epistemic states (`NOT_CONFIGURED`, `DATA_UNAVAILABLE`, `INSUFFICIENT_EVIDENCE`, `SOURCE_ERROR`). Never silently substitute arbitrary guesses or synthetic metrics.
5. **No-Bypass Verification:** Build and integrity verification tools must directly inspect repository facts. Flags such as `--force-pass`, `skipIntegrity=true`, or bypass environments are strictly prohibited.

## 2. Canonical Epistemic States

Every data point, observation, analysis result, or claim in the system must be tagged with an unambiguous epistemic state:

| Epistemic State | Definition & Governance |
| :--- | :--- |
| `OBSERVED` | Raw, un-manipulated empirical signal directly extracted from an authorized source record or audio waveform. |
| `MEASURED` | Quantitative numerical value calculated directly from raw observed signal via deterministic, versioned algorithms. |
| `DERIVED` | Analytical or aggregate conclusion computed from multiple measured features across a frozen cohort. |
| `SOURCE_REPORTED` | Factual claim reported by an authoritative third-party source (e.g., chart positions, release dates) without local acoustic re-measurement. |
| `AI_DRAFT` | Creative suggestion, lyrical phrase, or preliminary classification generated by an AI model (e.g., Gemini); requires human or rule review before promotion. |
| `AI_CLASSIFIED` | Categorical classification or tag assigned by a validated model against an approved prompt/schema version. |
| `INFERRED` | Statistically modeled property with quantified confidence and margin of error. |
| `HUMAN_REVIEWED` | Item, slang term, genre edge, or artist profile curated and explicitly approved by a domain researcher. |
| `VERIFIED` | Full cryptographic and algorithmic verification complete; backed by immutable evidence lineage. |
| `CONTRADICTED` | Feature observation where conflicting authoritative sources disagree; preserved in unresolved audit queues. |
| `UNRESOLVED` | Ambiguous identity, genre assignment, or metadata record pending reconciliation. |
| `NOT_AVAILABLE` | Required observation could not be collected due to source absence, permission boundaries, or lack of coverage. |

### Promotion Law
- Data in `AI_DRAFT` may **never** be promoted directly to `MEASURED` or `OBSERVED`.
- Data in `UNRESOLVED` or `CONTRADICTED` may never be incorporated into published DNA snapshots.

## 3. Provider Integration States

External API connections (Gemini, Spotify, Billboard, Genius, etc.) must transition only through explicit, observable runtime states:

| Provider State | Operational Meaning |
| :--- | :--- |
| `NOT_CONFIGURED` | Required API key, token, or environment secret is missing from `.env` and environment variables. |
| `CONFIGURED_UNVERIFIED` | Secret exists in environment but has not completed a live ping/handshake. |
| `AVAILABLE` | Provider credentials verified via a successful, authenticated live check within the validity window. |
| `DEGRADED` | Provider is responding with elevated latency (> 2500ms) or intermittent errors. |
| `RATE_LIMITED` | Provider responded with 429 Too Many Requests; backoff policy active. |
| `AUTH_FAILED` | Provider rejected configured credentials with 401 Unauthorized or 403 Forbidden. |
| `SOURCE_ERROR` | Provider endpoint responded with 5xx server failure or malformed payload. |
| `DISABLED_POLICY` | Provider disabled by administrative configuration or licensing policy. |

## 5. Phase Verification & Receipt Law

Every phase in the implementation sequence (`P-01` through `P48`) produces a cryptographic machine-readable receipt at `docs/implementation/evidence/{PROMPT_ID}_RECEIPT.json`.
- A phase cannot be declared `PASS` unless all verification commands designated `BLOCKER` in `docs/implementation/INTEGRITY_CHECK_MATRIX.csv` succeed with exit code `0`.
- All checks must be recorded with exact execution timestamps, commands, and exit codes.
- Future/non-applicable checks must be explicitly marked `NOT_APPLICABLE` with a reason.
